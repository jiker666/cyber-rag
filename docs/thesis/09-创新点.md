# 09 创新点(第四轮: Security-Aware Adaptive RAG)

> 本轮创新点围绕**低延迟、可控开销的自适应检索增强问答**。区别于 08 篇的工程化创新,
> 本篇三个创新点均为**检索策略与算法层**的贡献, 且全部在系统中真实落地、可消融、可复现。
> 实验数据见 06 篇 E5/消融/小到大实验(真实运行产出, 未达标处如实呈现)。

## 创新点 1: 面向网络安全领域的实体感知自适应检索

将"查询理解"从黑盒 LLM 分类改为**零 LLM、亚毫秒、可解释**的规则分析器, 并以分析结果驱动检索路径选择:

### 1.1 Security-Aware Query Analyzer(纯规则)

- **安全实体识别**: 正则 + 领域词典抽取 CVE/CWE/CAPEC/ATT&CK/OWASP 五类标识符与术语(如 `CVE-2021-44228`、`CWE-79`、`T1190`、`sql注入`), 输出实体列表、类型分组与参与精确匹配的标识符集合;
- **查询类型判定**: 六类 `{EXACT_ENTITY, FACTUAL, PROCEDURAL, CONCEPT, COMPARATIVE, MULTI_HOP}`, 由关键词规则(疑问词/比较词/流程词/多跳连词)与实体信号共同决定;
- **复杂度评分**: 句长、实体数、连词数、疑问维度数的加权评分, 作为路由与上下文预算的连续信号;
- **全链路可解释**: 分析结果(queryType/complexity/entities/confidence)完整落入 Performance Trace 与数据库, 前端"本次 RAG 决策"面板直接展示——用户可见每一次路由的依据, 而非不可解释的黑盒决策。

不使用 LLM 做查询分类的理由: 分类延迟(秒级)远大于其收益, 且规则方法在安全领域的封闭词表上准确率可由单测保证(`test_analyzer.py` 全类型覆盖)。

### 1.2 Adaptive Retrieval Routing(四路径)

依据查询类型 + 复杂度 + 实体信号, 在检索前选择开销递增的路径, 实现"简单问题走快路, 复杂问题走全路":

| 路径 | 触发条件 | 检索方案 | 设计动机 |
|------|----------|----------|----------|
| **EXACT** | 精确实体命中(如 CVE 编号) | BM25 优先 + 实体精确加权(+0.03 RRF 加成) | 标识符类查询词面匹配即语义, 向量反而引入噪声 |
| **FAST** | FACTUAL 且低复杂度 | 仅向量 Top-3, 高置信直接跳过 BM25/RRF/重排 | 简单事实无需重型管线, 置信不足自动升级 HYBRID |
| **HYBRID** | 其余(CONCEPT/PROCEDURAL/COMPARATIVE/升级) | 向量 ∥ BM25 → RRF(k=60) → 门控重排 | 兼顾语义与词面, 重排由置信度按需触发 |
| **DECOMPOSE** | MULTI_HOP 且复杂度 ≥ 阈值 | LLM 分解 2-3 子查询 → 子查询混合检索 → 跨子查询 RRF → 单次重排 | 多跳问题单次检索无法覆盖; 仅此路径使用 LLM 辅助, 且有阈值门控防止滥用 |

### 1.3 Security Entity Boost

EXACT/HYBRID 路径下, 候选中文档名或内容精确命中查询实体标识符的片段获得 RRF 加权(+0.03), 使 `CVE-2021-44228` 这类查询优先返回专门讨论该漏洞的文档而非 merely 提及的文档。消融开关 `entityBoost` 可单独关闭以量化收益。

## 创新点 2: 基于检索置信度的动态重排序门控

固定重排(每次都跑 CrossEncoder)在小问题上开销显著且收益有限。本系统将"是否重排"建模为**检索前信号 + 检索后信号的两级门控**:

### 2.1 门控信号与决策函数

```
need_rerank = f(top1_score, score_margin, vector_bm25_agreement, query_complexity, candidate_count)
```

- **top1_score**: 融合(或重排)后首候选得分——首候选已足够好时无需重排;
- **score_margin**: top1 与 top2 分差——分差大说明排序已稳定;
- **vector_bm25_agreement**: 双路 Top-5 重合率——两路一致说明结果鲁棒;
- **query_complexity / candidate_count**: 复杂问题与多候选倾向重排。

策略输出三态 `skip / auto / force`: 优先级规则(8 条, 全部阈值入配置 `rerank_*`)决定; `auto` 态由检索后实际信号复核, FAST 路径置信不足时自动升级 HYBRID 并按其策略执行。

### 2.2 证据置信度

融合后信号加权合成 `retrievalConfidence ∈ [0,1]`:

```
confidence = 0.55·top1 + 0.20·agreement + 0.15·min(margin/0.15, 1) + 0.10·min(n/K, 1)
```

重排发生时以 sigmoid 将 CrossEncoder 分数混合 top1 信号。置信度三档(充分 ≥0.65 / 一般 ≥0.40 / 不足)具有双重作用:

1. **低延迟**: 高置信跳过重排(设计目标激活率 <60%; 实测 93.3%, FAST 阈值按真实
   分布再标定(0.72→0.55)后复测 86.7%——剩余门控在分析器类型层("什么是X?"判
   CONCEPT 走全路, 属设计语义), 未达目标的原因分层记录于 06 §7.7 修复与再标定节;
   消融显示门控跳过 20% 重排时关键词命中率反升 5.3pp, "低置信才重排"的质量逻辑成立);
2. **可信生成**: 置信度不足时, 生成提示追加低证据约束("当前知识库中没有足够证据, 不得编造"), 把检索质量信号传导到生成端抑制幻觉。

### 2.3 与既有工作的差异

常见做法是全量重排或按 Top-K 阈值粗切; 本方案的创新在于**多信号连续函数 + 两级门控 + 证据分级传导**, 且每个阈值可配置、每个决策(含原因字符串)入 trace, 消融实验可单独关闭(`rerankGating=false` 回退固定开关)。

## 创新点 3: 面向低延迟的动态上下文构建

### 3.1 Small-to-Large Context Retrieval(父块召回)

- **两级索引**: 入库时 Parent(1024 字符, overlap 100)→ Child(320 字符, overlap 60), 仅 Child 向量化入库, Child 元数据携带 `parent_chunk_id + parent_text`;
- **检索用小块, 生成用大块**: 子块命中后按 `(kb_id, document_id, parent_chunk_id)` 复合键去重并替换为父块全文——检索精度来自小块(语义集中), 上下文完整度来自大块(论证完整);
- **引用保真**: 替换只改送入 LLM 的内容, 引用仍标注原文档名/页码, 用户核验不受影响。

对比固定分块的固有矛盾(小块检索准但断章, 大块完整但检索稀释), 该方案解耦两个目标; 与 KB4/5/6 的固定 256/512/1024 对照见 06 篇小到大实验。

### 3.2 Dynamic Context Budget(预算式上下文)

不把 Top-K 结果全部塞进提示词, 而是按查询复杂度分配 token 预算:

1. **近重复合并**: 相邻 chunk_index 的同文档片段合并为连续上下文; 三元组 Jaccard 相似度 > 阈值的近似重复块去重;
2. **预算分配**: `budget_chunk_count = f(complexity)`——简单问题 2-3 块, 复杂问题 4-6 块(上限受 top-K 约束), 逐块累加启发式 token 估算(CJK 0.75/字符, ASCII 0.28/字符)直至预算用尽;
3. **裁剪可观测**: 被裁剪块数、最终上下文块数与 token 数全部入 trace(`droppedChunks/finalContextCount/contextTokens`), 评测逐题记录——上下文缩减是可审计的数字而非模糊声称。

收益方向: 上下文 token 缩减直接降低提示词长度, 带来生成延迟与成本下降, 并减少无关信息对生成的干扰。

## 工程优化(非算法创新, 论文中如实定位)

以下为支撑低延迟的工程手段, **不计入创新点**, 仅作为系统贡献陈述:

| 优化 | 实现 | 说明 |
|------|------|------|
| 真并行混合检索 | ThreadPoolExecutor 并行向量/BM25 两路 | 检索墙钟时间由"两路之和"变为"两路之最大" |
| Embedding LRU 缓存 | 查询向量记忆化 | 相同问题零 embedding 开销 |
| 版本感知检索缓存 | key 含 kb_versions, 入库/删除 bump 版本 | 不依赖 TTL, 知识库变更即失效; 只缓存融合候选, 门控/重排每次真实执行 |
| CrossEncoder 批量 + 预热 | 启动后台线程首推理 | 消除首请求冷启动尖刺 |
| SSE 流式回答 | Python→Java→前端三级事件流 | 首字延迟(TTFT)从"总时长"降为"检索+首 token", 交互体验质变 |

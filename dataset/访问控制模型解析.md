# 访问控制模型:从 DAC 到零信任

## 为什么需要访问控制模型

认证回答"你是谁", 访问控制回答"你能做什么"。不同的业务场景需要不同强度与灵活度的授权模型。

## 经典模型

### DAC(自主访问控制)

资源所有者自行决定谁能访问(如 Linux 文件权限、分享链接)。
灵活但难审计, 权限可传递扩散, 不适合企业核心数据。

### MAC(强制访问控制)

系统按安全等级强制决策(如军事系统的密级: 公开<秘密<机密)。
严格但运维成本高, 适用于高保密场景。

### RBAC(基于角色)

最主流的企业模型: 用户 → 角色 → 权限。

```
用户(admin) → 角色(ADMIN) → 权限(user:manage, kb:delete)
用户(alice) → 角色(USER)   → 权限(kb:read, chat:ask)
```

优点: 便于职责分离、批量管理; 缺点: 角色爆炸(细粒度需求导致角色数量失控)。

### ABAC(基于属性)

按主体属性(部门/职级)、客体属性(密级/归属)、环境属性(时间/IP/设备)动态决策:

```
允许 当 主体.department == 客体.department
     且 当前时间 ∈ 工作时间
     且 设备 ∈ 已注册设备
```

适合复杂动态场景, 实现与调试成本较高。实践中常与 RBAC 混合(RBAC 定大框架, ABAC 做例外与细化)。

## 最小权限原则

任何主体只持有完成当前任务所必需的最小权限, 并且:

- 默认无权限, 显式授予
- 权限定期复核(recertification), 离职/转岗及时回收
- 高危操作二次审批或双人复核
- 临时权限(救火提权)有时效, 到期自动回收

## 零信任架构(ZTA)

"永不信任, 始终验证"的核心原则:

1. 不再以"是否在内网"作为信任依据, 内外一视同仁
2. 每次访问都认证与授权, 决策基于身份+设备+环境+行为
3. 微分段: 资源级隔离, 限制横向移动
4. 持续评估: 会话期间行为异常即降权/中断

落地组件: 统一身份(IdP + MFA)、SDP/微隔离、设备合规检查、策略引擎。

## 在本系统中的应用示例

- RBAC 双角色: ADMIN(管理用户/知识库/评估任务)、USER(问答/反馈)
- 接口级: 拦截器校验角色注解; 数据级: 会话与用户绑定, 他人不可见
- 未来扩展: 知识库级 ACL(哪些用户组可检索哪个库)即 ABAC 思想的落地

# 安全漏洞报告(CVE)生命周期

## CVE 与 CVSS 的关系

- **CVE**: 漏洞的全球唯一编号(如 CVE-2021-44228), 解决"同一个漏洞多个名字"的问题
- **CVSS**: 漏洞严重性评分(0-10), 分基础/时间/环境三个维度
- **CNA**: 有编号分配权的机构(厂商、MITER、CNNVD 等)
- **NVD/CNNVD/CNVD**: 漏洞库, 收录详情与受影响产品信息

## 生命周期各阶段

```
发现 → (保密期)报告厂商 → 厂商确认与修复 → 编号分配(CVE/CNVD)
     → 协调披露(Coordinated Disclosure, 通常 90 天)
     → 公开公告 + 补丁 → 攻防对抗期(1-day 利用激增) → 长尾消化
```

## 研究者合规披露流程

1. 确认漏洞真实存在(有可复现证据, 无误报)
2. 通过厂商 SRC/PSIRT/安全邮箱报告, 内容含: 影响版本、复现步骤、危害评估
3. 约定保密期, 等待厂商修复与公告
4. 公开时间协商一致(避免补丁未发布就曝光)
5. 严禁: 未经披露前公开细节、售卖漏洞给黑产、利用漏洞实际入侵

## 使用者侧的漏洞运营

1. **订阅情报**: NVD/CNNVD RSS、厂商公告、商业情报
2. **资产映射**: 漏洞公告 → 我有哪些资产用了受影响组件(SCA 清单是前提)
3. **风险评估**: CVSS 只是起点, 结合暴露面(是否公网)、利用难度、在野利用情报
4. **处置决策**: 
   - 有补丁: 按优先级升级
   - 无补丁: 临时缓解(WAF 规则、关闭功能、网络隔离)
   - 复测验证修复有效
5. **沉淀**: 处置记录入库, 更新扫描规则

## 典型案例启示: Log4Shell (CVE-2021-44228)

- 影响面: Log4j2 被无数 Java 应用间接依赖, 波及全球
- 利用门槛极低: JNDI 注入一行字符串
- 启示: 依赖清单(SBOM)决定你能否在 24 小时内回答"我哪里用了它"; 临时缓解(setting `log4j2.formatMsgNoLookups`)为升级争取时间

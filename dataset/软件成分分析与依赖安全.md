# 软件成分分析(SCA)与依赖安全

## 为什么依赖是重大风险

现代应用 70%+ 的代码来自开源组件。依赖链的脆弱性在于:

1. **传递依赖**: 你引入 A, A 引入 B, B 引入 C —— 你审计过 C 吗?
2. **已知漏洞**: 历史版本组件携带 CVE(如 Fastjson、Log4j2、Spring 系列)
3. **恶意包**: typosquatting(仿冒知名包名)、劫持维护者账号投毒
4. **停止维护**: 无 issue 修复、无安全补丁的僵尸依赖

## SCA 是什么

Software Composition Analysis: 扫描项目的依赖清单与制品, 对比漏洞数据库, 输出:

- 依赖树(含传递依赖)
- 已知 CVE 列表与严重等级
- 许可证合规检查(GPL 传染性等)
- 修复建议(升级版本/替代组件)

## 各语言生态的清单文件

| 生态 | 清单 | 锁定文件 |
|------|------|---------|
| Java/Maven | pom.xml | (可用 dependencyConvergence) |
| Python | requirements.txt | pip-tools/poetry.lock |
| Node | package.json | package-lock.json / pnpm-lock.yaml |
| Go | go.mod | go.sum |

锁定文件必须提交仓库, 保证构建可复现且依赖不漂移。

## 实践流程

1. **引入门槛**: 新依赖评审(维护活跃度、社区规模、许可证、历史漏洞记录)
2. **持续扫描**: CI 中 SAST/SCA 门禁, 高危 CVE 阻断合并
3. **升级策略**: 主动小步升级(而非被迫大版本跨越), 关注 breaking change
4. **无法升级时**: 评估缓解措施并记录风险接受决策
5. **应急响应**: 重大 CVE 爆发时, 通过 SBOM 快速定位受影响服务

## 常见 Java 高危历史漏洞速记

- Fastjson: 多轮反序列化 RCE, autoType 绕过史
- Log4j2 <2.15: JNDI 注入 RCE(Log4Shell)
- Spring4Shell (CVE-2022-22965): 特定条件下的 RCE
- Struts2: OGNL 注入系列 RCE
- Shiro: rememberMe 反序列化系列

启示: 组件安全 = 版本管理 + 及时情报 + 快速响应能力。

# 安全事件响应案例复盘模板

## 为什么需要复盘

复盘(Retrospective)的目的是改进系统与流程, 而非追责。无复盘的响应只解决了这一次事件, 有复盘的响应消除一类事件。

## 案例一: 凭证泄露导致数据被拖

### 事件时间线(示例模板)

```
D0 14:02  攻击者使用有效 API Key 从异常 IP 访问对象存储
D0 14:05  批量下载行为开始(高 QPS 大流量)
D0 18:30  运维发现流量异常, 人工确认
D0 18:35  吊销泄露 Key, 阻断攻击 IP
D0 19:00  评估影响范围: 3 个桶约 20GB 数据
D1 09:00  确认 Key 来源: 开发人员误提交到公开仓库
D2        - 完成取证, 发布公告, 启动整改
```

### 根因分析(5 Why)

1. 为什么数据被拖? → 泄露的 Key 有读权限
2. 为什么 Key 泄露? → 硬编码提交到公开仓库
3. 为什么没有拦住? → 仓库无密钥扫描
4. 为什么没及时发现? → 无对象存储异常访问告警
5. 为什么权限这么大? → 未做最小权限收敛

### 整改措施

- [ ] 仓库接入密钥扫描(推送即阻断)+ 历史 commit 清理
- [ ] 所有密钥走 KMS/环境变量, 禁止入库
- [ ] 对象存储接入审计日志与异常告警(阈值: 单 Key 5min 下载 >1GB)
- [ ] Key 定期轮换(90 天)+ 泄露响应演练

## 案例二: 钓鱼邮件导致账号接管

### 时间线要点

员工点击钓鱼链接并输入 MFA 码 → 攻击者登录企业 SaaS → 横向访问代码仓库 → 试图窃取客户数据被风控拦截。

### 根因

1. 钓鱼演练缺失, 员工对实时钓鱼 MFA 疲劳攻击无认知
2. SaaS 会话无设备绑定, 异地登录无强制挑战
3. 代码仓库访问未纳入统一审计

### 整改

- [ ] MFA 升级为抗钓鱼方式(FIDO2 硬件密钥)
- [ ] 条件访问: 异地/新设备登录触发二次验证
- [ ] 季度钓鱼演练 + 靶向培训
- [ ] SaaS 资产纳管, 统一 SSO 与审计

## 复盘会议要点

- 时间线上不上线, 参会人覆盖发现/处置/受影响各方
- 无责文化: 对事不对人, 否则下次没人报告
- 每条整改有 owner 与 deadline, 定期跟踪闭环
- 更新预案与检测规则, 沉淀知识库
